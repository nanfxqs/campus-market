## Problem Statement

校园二手交易平台已完成 V1 功能基线验收，但还没有正式证明完整数据规模下的成交性能，也缺少统一的功能耗时、存储和内存实测以及可复查的课程实验报告。课程要求约 10,000 用户、20,000 件在售商品、180,000 件历史成交商品与 300,000 条交易记录；仅有 20,000 件在售商品不足以完成已确认的 30,000 次新增成功成交，需要明确区分基础数据与压测扩展数据。

项目还需要通过实际使用 Redis 练习 NoSQL 缓存，通过 Nginx 与多 Gin 实例学习负载均衡。引入这些组件不能破坏卖家确认线下成交、商品只能成交一次、幂等、到期立即禁止成交及卖家当前信息等既有语义，也不能在没有实测证据时预设性能提升。

## Solution

交付 V2 正式性能验收、Redis 商品资料版本缓存、Nginx 加双 Gin 负载均衡演示、统一测量与完整原始实验材料，以及只包含正文的 Markdown 课程实验报告。以现有 HTTP API 为主要验证边界，继续使用真实 MongoDB、Search 和数据库外部核验。

在完整基础数据上追加至少 30,000 件专用在售商品，使用 Locust 对单 Gin 无缓存、单 Gin 有缓存、Nginx 加双 Gin 有缓存三组配置分别完成三轮正式成交验收；另做同商品竞争、同键重试、详情缓存读取、Redis 故障与八项核心功能计时。Redis 为必做课程练习，Nginx 与双实例为必做系统设计学习演示；性能不一定改善，实验必须如实记录。NoSQL 实验详细分析，负载均衡仅在正文中简述分析，实际测试及结果记录不缩减。

## User Stories

1. As a 验收人员, I want 复用已通过的 V1 功能基线, so that V2 不会重新定义已确认的业务语义。
2. As a 验收人员, I want 一条命令启动选定实验配置, so that 环境无需手工拼装。
3. As a 验收人员, I want 可执行的完整数据生成与导入入口, so that 实验包含题目要求的数据特征和规模。
4. As a 实验人员, I want 在完整基础数据上追加至少 30,000 件专用在售商品, so that 足够执行 30,000 次不同商品的成功成交。
5. As a 实验人员, I want 区分基础种子规模与压测扩展规模, so that 报告不会把 50,000 件在售写成题目原始要求。
6. As a 实验人员, I want 固定随机种子与记录时间基准, so that 每轮初始状态能够复现。
7. As a 实验人员, I want 每轮重置指定实验数据库及专用缓存, so that 上一轮成交和缓存不会污染下一轮。
8. As a 维护人员, I want 重置显式指定且只影响实验资源, so that 实验不会删除其他项目数据。
9. As a 实验人员, I want 导入与只读核验完成后再启动业务负载, so that 部分导入不会被误当作有效初始状态。
10. As a 实验人员, I want 重置后重新登录并完成准备, so that 正式负载不会使用失效令牌。
11. As a 验收人员, I want 50 个 Locust 虚拟用户全部就绪后统一计时, so that 600 秒窗口不混入登录、启动和预热。
12. As a 验收人员, I want 每个用户串行连续发起成交且不设置思考时间, so that 并发口径明确。
13. As a 验收人员, I want 每轮在 600 秒内完成至少 30,000 件专用商品的新增成功成交, so that 达到确认的性能目标。
14. As a 验收人员, I want 三组配置各重复三轮且每轮均达标, so that 偶然成功不能替代稳定验收。
15. As a 验收人员, I want 幂等重试和历史成交不重复计入成功数, so that 成交量反映真实新增结果。
16. As a 验收人员, I want 核对客户端结果与数据库新增成功记录、商品状态和卖家成交数, so that HTTP 成功不掩盖数据不一致。
17. As a 验收人员, I want 单独核对超时但最终提交的请求, so that 数据库成功不会被误报成客户端按时完成。
18. As a 验收人员, I want 获得吞吐量、P95/P99、错误率及服务端辅助指标, so that 性能结论可以复查。
19. As a 验收人员, I want 100 件商品分别承受 50 个不同幂等键的同步竞争请求, so that 能直接验证没有超卖。
20. As a 验收人员, I want 每个竞争组恰好一次成功、49 次业务冲突并核对数据库, so that 唯一成交具有完整证据。
21. As a 卖家, I want 相同幂等键重试仍只产生一次成交, so that 网络重试不会重复记录或增加成交数。
22. As a 学生, I want 商品详情缓存较稳定资料, so that 能通过实际实验观察 Redis 的作用。
23. As a 学生, I want 详情中的当前价格、成交状态、在售资格、卖家信息和最近改价记录仍保持原有语义, so that 缓存不会使动态信息失真。
24. As a 卖家, I want 编辑商品资料后新读取不复用旧版本缓存, so that 商品展示与成功编辑一致。
25. As a 维护人员, I want 缓存使用资料版本隔离并处理并发编辑, so that 较早读取不会把旧资料写成当前版本。
26. As a 维护人员, I want Redis 不可用时读取回退 MongoDB, so that 缓存故障不会阻断正常业务。
27. As a 维护人员, I want 缓存写入失败不改变业务成功结果, so that 辅助组件不会改变持久化事实。
28. As a 实验人员, I want 缓存有效期、内存上限和淘汰策略明确且可配置, so that 实验资源受控。
29. As a 实验人员, I want 比较无缓存、冷缓存和热缓存, so that 不把预热效果误当作普遍收益。
30. As a 实验人员, I want 分别测试固定热点和完整商品集上的分散访问, so that 命中率不只来自重复读取一个商品。
31. As a 实验人员, I want 记录命中率、查询次数、数据读取量、吞吐量及延迟, so that 能解释缓存收益有限或变慢的原因。
32. As a 实验人员, I want 实际停止及恢复 Redis 并验证读取、编辑和成交, so that 故障回退得到真实验证。
33. As a 系统设计学习者, I want Nginx 将请求轮询分发到两个 Gin 实例, so that 能观察负载均衡效果。
34. As a 卖家, I want 登录令牌与幂等重试在不同实例间有效, so that 无会话粘滞也能正常交易。
35. As a 系统设计学习者, I want 对比每实例资源相同的单实例与双实例, so that 能观察增加应用总资源后的扩容效果。
36. As a 实验人员, I want 明确代理与实例数同时变化以及应用总资源增加, so that 不把全部差异归因于 Nginx 或资源效率。
37. As a 验收人员, I want 八项核心功能各有可执行入口与统一计时, so that 功能性能可独立复查。
38. As a 验收人员, I want 单独观察到期资格失效和 TTL 清理延迟, so that 不把后台清理等待误当作接口延迟。
39. As a 验收人员, I want 实测应用、MongoDB、Search、Redis 和 Nginx 的资源占用, so that 存储和内存结论不是估算。
40. As a 实验人员, I want 记录机器、Docker 资源预算、软件版本和实际数据规模, so that 性能结果具有环境上下文。
41. As a 验收人员, I want 保存全部正式运行、失败及调优原始输出, so that 报告没有选择性展示结果。
42. As a 课程学习者, I want Markdown 正文解释数据库选型、索引、结构与缓存取舍, so that NoSQL 学习成果有完整依据。
43. As a 系统设计学习者, I want 负载均衡分析简短但链接完整测试结果, so that 正文突出 NoSQL 而实验材料仍完整。
44. As a 维护人员, I want 将跨机器验证保留为最后评估的待考虑项, so that 不会把本机重建误报成第二台机器验证。

## Implementation Decisions

- **既有契约与模块**：扩展环境编排、种子生成与导入、商品详情及资料编辑、压测与测量、外部核验和实验报告模块。沿用现有 REST API、认证、所有权、分类校验、中文同义词搜索、改价历史及错误语义；更新运行配置和相关 API 文档，不为压测新增公开测试接口。
- **架构约束**：继续使用本地 MongoDB Search 和经验证的固定 Atlas Local 镜像；独立在售条目由 TTL 最终清理，所有相关业务即时检查期限。成交仍由 MongoDB 条件更新和事务共同提交商品成交信息、资格移除、成功交易记录及卖家成交数；Redis 不承担成交裁决、幂等持久化或当前业务事实来源。保留已有五项 ADR 的决定。
- **三组配置**：A 为单 Gin、关闭 Redis 缓存、HTTP 直接访问；B 为单 Gin、开启 Redis 缓存、HTTP 直接访问；C 为 Nginx 加两个 Gin、开启 Redis 缓存。当前机器 Docker Compose 部署，共用同一套 MongoDB、Search 与 Redis。Nginx 轮询、不使用会话粘滞；应用实例不依赖本机独有的登录或幂等状态。
- **扩容资源口径**：B/C 的每个 Gin 实例 CPU、内存配置相同，C 的应用总资源因此增加；MongoDB、Search、Redis 配置相同，Nginx 开销另计。A/B 使用相同应用配置。记录具体资源预算，不将 B/C 解释为相同总资源下的效率比较，也不将全部差异归因于 Nginx。
- **数据集**：保留约 10,000 用户、20,000 件基础在售商品、180,000 件历史成交商品、300,000 条交易记录，另加至少 30,000 件专用有效在售商品。继续体现异构属性、中文错别字及同义词、卖家信息变化、1–9 张图片地址和平均 2–3 次改价。复用已有用户，专用商品与基础商品可明确区分，负载只成交专用商品。现有仅含 30,000 件在售、无历史数据的 stress 数据集不能替代正式验收数据。
- **规模变化**：准备恰好 30,000 件专用商品时，压测开始约 50,000 件在售、180,000 件已成交、300,000 条交易记录；完成全部专用商品后约 20,000 件在售、210,000 件已成交，交易记录至少增加 30,000 条，业务失败产生的记录另外统计。报告各集合实际数量、改价记录和有效资格数量，不把基础历史计为新增成交。
- **每轮恢复**：使用固定随机种子及显式记录的时间基准恢复相同初始状态，期限须覆盖全部实验。初始化拒绝非空数据库；重置必须显式指定且仅作用于指定实验数据库及专用缓存。重置和导入期间停止相关业务服务，导入成功并通过只读核验后再启动；重新登录，检查令牌时效、数据库健康和 Search 收录就绪。准备、登录、启动、收录等待与预热耗时单列，不计入正式窗口。
- **正式负载**：Locust 50 个虚拟用户，各自串行连续发起卖家确认成交请求，不设思考时间；使用合法卖家身份、其他已注册买家及合法成交价。全部用户就绪后统一计时，截止 600 秒。专用商品唯一分配，各商品使用唯一幂等键，重试沿用原键及内容。正式测试只压成交，混合其他功能的负载不作为必交项。
- **重复与通过标准**：A/B/C 各做三轮正式验收，每轮恢复相同初始状态，每轮须在窗口内完成至少 30,000 件专用商品的新增成功成交，且成交一致性核验通过。保留每轮输出和失败后的调优运行，不能以平均值或最好一轮掩盖失败；未达标则如实报告并继续基于证据调优，不降低标准。
- **计数与计时**：客户端按窗口内收到成功响应的唯一新增成交商品计数；历史成交和幂等重复响应不重复计入。单独核对超时或窗口后才获响应但数据库最终提交的结果，不直接计为客户端按时成功。报告端到端请求吞吐量、新增成功成交吞吐量、P95/P99、错误率、重试、业务冲突及其他错误，说明样本范围及统计方法；成功、冲突与其他失败分别报告，附服务端辅助指标。无额外 P95/P99 合格门槛。
- **竞争实验**：独立使用 100 件有效在售商品，每件接受 50 个同步发起、不同幂等键的有效请求；每组必须恰好一次成功、49 次业务冲突，数据库仅一条成功记录、卖家成交数只增加一。基础设施错误单独报告，该组不能算通过。另做同键同内容重试，允许多个成功响应但只产生一次成交及计数。
- **缓存范围**：仅缓存商品详情较稳定资料，即标题、描述、图片、分类及扩展属性；其他已有资料字段保持完整详情响应，未明确缓存的字段默认走 MongoDB。当前价格、成交状态与信息、在售资格、卖家当前资料及最近改价记录仍实时从 MongoDB 获取并组装。浏览、搜索、卖家主页、分类统计暂不缓存，不新增排行榜、限流或其他业务功能。
- **资料版本与并发**：为商品资料引入内部版本，创建、种子与已有数据兼容初始化规则明确；编辑资料时与资料更新原子递增版本。缓存键按商品 ID 与资料版本隔离。详情先读取当前动态字段和资料版本，再获取对应版本缓存；未命中时读取匹配版本的资料，若期间发生编辑则重新获取一致版本或回退完整数据库读取，不能把旧资料标成新版本。并发读取无需升级为跨集合事务快照，但编辑提交后开始的新读取不能复用旧资料版本。旧版本自然到期，无须依赖删除缓存裁决一致性。
- **缓存收益边界**：当前详情串行读取商品、卖家、有效资格及最近改价记录；只缓存资料仍需商品动态信息查询。命中时采用适当字段投影减少资料读取，未命中可能增加查询。记录查询次数和数据读取量，明确测量口径，不承诺减少查询次数、降低延迟或提升成交吞吐量。
- **缓存配置与故障**：默认有效期 10 分钟、Redis 内存上限 128 MiB、allkeys-lru 淘汰，均可配置。实验使用专用 Redis 实例，每轮数据重置清空对应实验缓存。缓存访问采用有限超时；Redis 不可用时回退 MongoDB，缓存写入失败不改变业务成功。记录命中、未命中、缓存错误与回退次数，MongoDB 自身失败仍按既有错误契约处理。
- **详情读取实验**：A/B 比较无缓存、冷缓存和热缓存；固定两组请求序列：固定 100 件商品的热点访问，以及按固定随机种子访问完整商品集的分散访问。各组使用 50 个虚拟用户运行 60 秒；同组不同配置的商品序列相同。冷缓存指计时开始为空、随后正常填充；热缓存指事先访问该组涉及商品后不清空，预热耗时另记。容量不足时不宣称全部命中，如实报告实际命中率。记录延迟、吞吐量、错误率、缓存命中率、MongoDB 查询次数和数据读取量；C 补充热点读取对比，完整冷/热实验重点放在 A/B。
- **故障实验**：正常性能实验之外实际停止 Redis，验证详情读取、资料编辑和成交仍符合契约；恢复后验证正常填充并不会返回编辑前资料。测试期间的故障与恢复证据单独保留，不混入正常验收统计。
- **八项功能计时**：发布、分类浏览、搜索、详情、卖家主页、成交、自动下架、分类统计各提供可执行查询或脚本，使用固定案例，单客户端预热后各测 100 次端到端 HTTP 耗时，报告中位数、P95/P99、错误率、机器与数据规模。发布、成交等写入使用独立商品，预热数据不混入正式统计；案例参数和查询结果校验有记录。自动下架的 HTTP 测量针对到期资格相关读取或拒绝行为，并另做 10 个到期样本的资格失效验证及 TTL 删除延迟观察，TTL 等待不能混入接口耗时。
- **资源测量**：记录 CPU、内存、磁盘、操作系统、Docker/Compose、应用、MongoDB、Search、Redis、Nginx、Locust 的版本及镜像标识；记录 Git 基点和工作区状态。导入完成的空闲阶段、成交负载阶段、详情读取阶段每秒采集应用、MongoDB、Search、Redis，以及 C 中 Nginx 和两个 Gin 实例的 CPU/内存，报告平均和峰值、单位及采集口径。MongoDB 与 Search 同容器时需要进程级区分，不能将同一容器总内存重复视为两者内存；另报告容器/整机信息及压测客户端开销。
- **存储测量**：压测前后实测数据库、Search 及相关持久卷占用，说明逻辑数据大小与文件/卷实际占用的区别；Redis 按真实配置报告内存及存在的持久化占用，无持久化卷则明确说明。保留测量命令、原始输出和时间戳，所有配置对比使用相同方法。
- **报告与材料**：Markdown 仅正文，包含选型、数据模型、全部功能依赖的索引/结构及原因、复现命令、实验环境、统计方法、完整结果链接、瓶颈分析及限制。Redis 和数据库实验重点分析；Nginx 加双实例仅正文分析简写，原始测试输出、完整指标、验证和分发演示不缩减。保留全部正式运行、失败及调优结果，无改善或变慢同样记录；不制作封面、目录或 Word。

## Testing Decisions

- **主要验证边界**：沿用真实 HTTP API 与可执行验收脚本，使用真实 MongoDB、Search、Redis 和 Nginx。测试关注响应、可观察持久化事实、恢复行为和统计结果，不绑定私有缓存函数、内部调用顺序或具体键字符串。数据库只读核验及外部到期夹具为辅助边界，不引入生产测试端点。
- **既有先例**：复用 V1 完整种子 HTTP 验收、发布与详情、资料编辑、改价、卖家主页、分类统计、搜索、成交并发与幂等、到期及真实 TTL 验证模式；统一部署验收已有隔离项目、导入后核验、错误诊断和清理归属保护。优先扩展这些入口，避免建立散落的新测试接口。
- **回归**：三种配置继续满足 V1 认证、所有权、输入校验、当前资料、改价历史、有效在售过滤、搜索总数与命中字段、精确金额、事务共同提交、幂等及到期规则；缓存开关不改变公开业务响应语义。
- **缓存一致性**：通过 HTTP 发布/读取/编辑/读取，验证缓存命中前后、并发编辑、旧读取晚完成、淘汰与重建、数据重置后不会返回错误版本。核验价格修改、卖家资料修改、成交与到期后动态字段仍正确；覆盖冷未命中、热命中、Redis 写入失败和不可达的行为。内部版本变化可作辅助数据证据，外部内容正确为主要断言。
- **跨实例**：通过 Nginx 登录及操作，展示请求到达两个实例；在一个实例获得的令牌可由另一实例验证，跨实例同键重试复用原结果，不重复成交或计数。不同幂等键竞争跨实例执行，遵守单商品唯一成交。
- **正式性能**：A/B/C 三组各三轮，50 用户与 600 秒窗口的真实 Locust 输出和时序完整保存。核验初始规模、唯一分配、合法身份、成交结果及各卖家计数增量；记录重试和超时最终提交，统计实现不能仅使用成功 HTTP 响应总数。
- **独立竞争**：100 组各 50 个同步请求，每组一次成功及 49 次冲突，逐组核验成功记录、档案状态、资格移除与卖家计数；基础设施失败不能伪装冲突。另验证同键重试多响应单事实，不将竞争失败率混入正常成交压测错误率。
- **计时与观察**：八项固定案例各预热后 100 次单客户端测量；详情热点/分散序列及冷/热状态可复现。10 个到期样本验证到期即时退出相关在售结果并拒绝成交，TTL 最终删除资格而保留档案及历史。使用有界观察与明确失败诊断，不把观察超时当成业务 TTL SLA，不把准备、Search 等待或 TTL 清理等待当作接口延迟。
- **资源与结果完整性**：核对每秒样本覆盖实验区间、进程与容器对应关系、卷归属及指标单位；报告可由原始材料复算。采集开销和压测端资源记录在案，三组采用同样测量方式，不凭单次截图或估算给出内存/存储结论。
- **实验隔离与故障**：初始化非空拒绝、重置范围受限、缓存清理与登录重建得到验证；失败导入不开始负载。停止/恢复 Redis 的独立实验验证回退和恢复后的当前资料，保留完整证据。正常通过后再运行故障实验或恢复干净状态，避免污染对比。
- **完成标准**：部署与种子入口可复现，三组各三轮成交均达标且一致性核验通过，竞争与同键验证通过，八项功能和详情读取实验、资源与存储采集、Redis 故障、跨实例行为及完整报告材料均交付。缓存与负载均衡无需证明一定加速；无额外延迟门槛。只在实际交付并验证后勾选路线图项目。

## Out of Scope

- 第二台物理机器的实际复现暂为最后评估的待考虑项，不作为本 spec 必交项；不得宣称已完成跨机器验证。本机多实例不扩展为跨机器集群。
- V3 终端 CLI、Cobra、Bubble Tea、独立网页前端。
- 新增排行榜、限流、消息队列、站内消息、支付、库存预占、订单履约、评价或信用算法。
- 用 Redis 替代 MongoDB 成交事务或幂等持久化，缓存浏览、搜索、卖家主页、分类统计及动态成交事实。
- 公开注册、统一登录、短信验证、找回密码、刷新令牌和令牌撤销；改变 V1 的所有权、认证或成交语义。
- 分类层级、重新上架、撤销成交、补录成交时间、图片上传、图片地址可达性检查、普遍错别字纠正或即时搜索收录承诺。
- 等总应用资源的单/双实例效率实验、生产高可用承诺、数据库/Search 多节点扩容；混合业务负载不是必须验收项。
- 学校封面、目录及最终排版、Word 文档；本轮只交付 Markdown 正文和实验材料。

## Further Notes

- 本 spec 根据 2026-10-10 已由用户最终确认的 V2 访谈合成，前置 V1 功能基线 spec #1 及子任务 #2–#13 均已关闭；V1 通过不等于 V2 性能通过。
- Redis 与 Nginx/多实例由此前“有瓶颈才添加”的规划改为必做学习实验。此变更不推翻 MongoDB 事务、独立 TTL 资格、本地 Search 等既有 ADR，也不预设学习组件产生性能收益。
- 三组共九轮正式成交验收；准备阶段、详情实验、竞争实验、故障实验和资源采集均有独立结果标识。完整原始材料在仓库或明确链接的位置保留，不能只留下正文摘要。
- 每实例相同资源是扩容对比，不是相同总资源；同机共享 CPU、内存、磁盘仍可能成为瓶颈，必须解释观测限制。
- 项目以 GitHub Issues 为可实施 spec 的权威来源，仓库保留同内容副本，后续变更需同步。
