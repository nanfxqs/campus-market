# 开发与验收计划

## 已确认的迭代边界

- V1 为功能基线版：先验证 MongoDB Search 与存储层自动下架的可行性，再完成数据建模、种子数据、8 项核心功能、REST API、Swagger UI、功能与并发正确性测试及一键部署。
- V2 完成正式压测、吞吐量与 P95/P99、存储与内存实测、8 项功能的可执行脚本与耗时、课程实验报告；先测基线，为课程练习加入 Redis 并对比前后性能、分析原因，另为系统设计学习加入 Nginx 和多个 Gin 实例并简述性能对比及效果演示，报告仍以 NoSQL 数据库实验为重点。
- V3 为可选 CLI 扩展，通过 HTTP 调用现有 API，使用 Cobra 和表格输出，复杂交互有实际需求后再考虑 Bubble Tea。

## 已确认的业务与验收口径

- V2 访谈补充（2026-10-10）：Redis 为必做课程练习，性能改善不是预设结论；跨机器验证放在最后评估，暂列待考虑项。
- V2 正式成交压测使用 50 个 Locust 虚拟用户，各自串行连续发起成交请求，不设置思考时间；登录、启动及预热在计时前完成，全部用户就绪后统一计时 600 秒，准备耗时另行记录。
- V2 正式成交验收重复 3 轮，每轮恢复相同初始状态，每轮均须在 600 秒内完成至少 30,000 次成功成交；保留所有正式运行结果及失败后的调优运行结果。
- V2 正式达标测试只压成交，8 项功能另行测量；混合负载为可选补充实验，不作为必过条件。
- V2 正式压测保留完整背景数据（约 10,000 用户、20,000 件在售商品、180,000 件历史成交商品、300,000 条交易记录），额外生成至少 30,000 件专用有效在售商品；报告压测前后完整数据规模，不以只有 30,000 件在售商品的独立数据集替代正式验收。
- V2 Redis 练习限定为现有读取功能的缓存，不新增排行榜或限流等业务功能；MongoDB 继续负责成交裁决、幂等与持久化。
- V2 同商品竞争实验使用 100 件商品，每件接受 50 个同步发起、不同幂等键的有效成交请求；每组须恰好 1 次成功、49 次业务冲突，并核验仅一条成功记录及卖家成交数仅增加 1。基础设施错误单独报告，该组不算通过；另测相同幂等键重试，核验多次成功响应只对应一次实际成交。
- V2 的 8 项功能在单客户端下使用固定案例，预热后各测 100 次 HTTP 客户端端到端耗时，报告中位数、P95/P99 与错误率；写入案例使用独立商品。自动下架另测 10 个到期样本，分别报告资格失效验证与 TTL 清理延迟，不把 TTL 等待混入接口延迟。
- V2 首轮 Redis 只缓存商品详情的稳定资料（标题、描述、图片、分类及扩展属性）；当前价格、成交状态、在售资格、卖家当前资料与最近改价记录从 MongoDB 读取并组装。浏览、搜索、卖家主页及分类统计暂不缓存。
- Redis 不可用时回退 MongoDB，缓存写入失败不影响业务成功；使用有限缓存访问超时，记录故障与回退次数。
- Redis 对比包含相同机器、数据和负载下关闭/开启缓存的成交验收，以及相同固定请求序列下无缓存、冷缓存、热缓存的商品详情读取实验；报告读取延迟、吞吐量、命中率和 MongoDB 查询次数，热缓存准备耗时单独记录。性能改善不是通过门槛。
- 资源测量覆盖导入后的空闲状态、成交压测与详情读取压测；每秒采集应用、MongoDB、Search、Redis 的 CPU 与内存，报告平均及峰值，压测前后测持久卷实际占用，所有对比使用相同采集方法。
- V2 Markdown 实验报告只记录正文，不包含封面、目录等信息；课程最终提交的格式处理不纳入本轮。
- Redis 缓存有效期默认 10 分钟，内存上限默认 128 MiB，采用 allkeys-lru 淘汰策略，均可配置；使用实验专用 Redis 实例，每轮重置数据时清空对应实验缓存。
- 商品详情读取实验包含固定 100 件商品的热点访问，以及按固定随机种子访问完整商品集的分散访问；各使用 50 个虚拟用户运行 60 秒，分别测无缓存、冷缓存、热缓存。冷缓存指开始时为空并正常填充；热缓存指预先访问该组涉及商品，预热耗时单列，容量不足时报告实际命中率。
- 正式成交按专用压测商品的新增成功成交计数，每件商品使用唯一幂等键，重试沿用原键；历史成交及幂等重试不重复计数。结束后核验新增成功交易记录、商品成交状态和卖家成交数，报告重试、业务冲突及其他错误；客户端超时但最终提交的请求单独核对，不直接计为客户端成功完成。
- 每轮成交实验开始时约 50,000 件在售、180,000 件历史成交，完成专用商品的 30,000 次新成交后约 20,000 件在售、210,000 件已成交；明确区分题目基础种子规模与压测扩展规模，每轮重置后重新登录。
- 商品资料可编辑，缓存不能视为不可变数据。编辑资料时在 MongoDB 中原子递增资料版本，缓存按商品 ID 与资料版本隔离；详情先读取当前动态字段和版本，再获取匹配版本缓存，未命中时读取匹配版本资料并处理并发编辑竞争。旧版本缓存自然到期；报告如实测量查询次数、数据读取量及性能，不承诺减少查询次数或加速。
- Redis 故障实验单独执行：停止 Redis 后验证详情读取、资料编辑及成交正确性；恢复后验证缓存重新填充且不返回编辑前的旧资料，不混入正常性能验收。
- Nginx 负载均衡与多个 Gin 实例作为必做系统设计学习演示，完整执行性能对比及效果演示，保留完整原始输出、指标和验证结果；仅 Markdown 正文中的结果分析与限制说明采用简短篇幅，并链接完整实验材料，不缩减实际测试及结果记录，不作为 NoSQL 课程报告侧重点。
- 当前机器上通过 Docker Compose 部署 Nginx 与两个 Gin 实例，共用 MongoDB、Search、Redis；Nginx 轮询且不使用会话粘滞，验证令牌和幂等重试跨实例有效，并演示请求分发到两个实例。不扩展为跨机器部署。
- 对比配置为 A（单 Gin、关闭 Redis 缓存、直接访问）、B（单 Gin、开启 Redis 缓存、直接访问）、C（Nginx 加两个 Gin、开启 Redis 缓存）。A/B 分析缓存影响，B/C 比较代理加双实例的整体变化，不将差异全部归因于 Nginx；三组各完成 3 轮正式成交验收。完整冷/热缓存详情实验重点放在 A/B，C 补充热点读取对比。
- B/C 使用每个 Gin 实例相同的 CPU、内存配置，因此 C 的应用总资源增加；这是增加应用资源后的扩容对比，不是相同总资源下的效率对比，不预设多实例必然更快。MongoDB、Search、Redis 配置保持一致，另行采集 Nginx 及两个 Gin 实例的资源占用；报告说明同机演示不代表跨机器扩容效果。

- 卖家确认线下成交，提交买家与成交价；商品只能成功成交一次。
- 交易记录包含成功和失败的成交尝试。种子数据约 18 万件历史成交商品对应成功记录，总计约 30 万条交易记录，其余为失败记录。
- 正式压测以 50 并发在 10 分钟内完成 3 万次成功成交为目标，另备至少 3 万件可成交商品，并明确报告运行时数据规模。
- 同商品竞争测试单独执行；报告成功、冲突与其他失败结果，分别说明耗时口径。
- 下架保留商品及历史，退出在售浏览、搜索和统计，并禁止成交；V1 不支持重新上架。
- V1 提供最小身份认证、所有权校验与种子账号；不包含学校统一登录、短信验证及找回密码。

## 确认状态与验证前置条件

V2 访谈已最终确认，并发布为 [V2 spec #14](https://github.com/nanfxqs/campus-market/issues/14)，标记 ready-for-agent；仓库副本见 [V2 spec](specs/v2.md)。后续实施及需求变更以 issue tracker 为准并同步副本。

设计访谈的决策与完整方案均已由用户最终确认。实现前须完成 MongoDB Search 和 TTL 在售条目方案的可行性验证；若验证不通过，应重新讨论相关决策，不静默替换方案。

## 第二轮已确认

- Docker Compose 使用本地 `mongodb/mongodb-atlas-local` 镜像，固定经验证的版本；先以要求的种子规模验证搜索能力与配置。
- 保留商品档案，将在售资格存入独立条目，由 TTL 删除到期条目；验证所有在售查询与成交的一致性后正式落定实现。
- 在售期限为发布时间加 60×24 小时；到期立即禁止成交，浏览、搜索和统计排除到期商品，TTL 负责后续物理清理。改价不续期，V1 不支持重新上架。
- 搜索只覆盖有效在售商品，保证中文分词和指定同义词集合，暂不承诺错别字纠正；按相关性返回前 20 条及有效在售范围内命中总数。
- 搜索结果包含 `matchedFields` 和命中片段，标题与描述可同时命中，同义词命中也计入；不要求逐词解释评分。
- 平台维护分类及属性类型、必填要求，允许额外属性；历史商品可读取，新增或修改按当前规则验证。
- 所有商品必填统一新旧程度：全新、几乎全新、轻度使用、明显使用；分类属性可补充品相说明。
- 交易记录只记录通过身份和参数校验的业务尝试，包括成功及已成交、已下架或到期等业务失败。认证、参数及基础设施错误记录日志；相同幂等键重试返回原结果，不新增交易记录。

## 第三轮已确认

- 成交以条件更新裁决竞争；商品成交信息、在售条目移除、成功交易记录与卖家成交数在同一数据库事务中提交，全部提交成功才返回成功。
- 买家必须为其他已注册用户，禁止自买自卖。成交价可不同于挂牌价，必须大于零，以人民币分为单位准确存储。
- 成交时间由服务端记录为确认时间，V1 不支持补录时间及撤销成交。
- 成交必须携带按卖家隔离的幂等键；同键同内容返回原结果，同键不同内容拒绝。成功及业务失败结果随交易记录保留，修改请求须用新键。
- 首次挂牌价单独保存；实际改价永久记录旧价、新价和时间，相同价格不新增记录。详情默认返回最近 5 次，另提供历史分页；只有卖家可修改其有效在售商品。
- 详情及主页展示卖家当前信息；在售数量按有效在售资格计算。V1 提供修改本人昵称、头像的接口，信用分为可复现的种子值，不引入评价及信用算法。
- V1 分类为平面结构，浏览按发布时间和商品 ID 倒序使用游标分页，默认 20 条、最多 100 条；分类浏览和统计只针对指定分类。
- 接受搜索收录的短暂延迟；返回前校验数据库当前在售资格，命中总数与前 20 条使用相同有效性条件，并在可行性验证中测量代价。
- 压测以 HTTP 客户端端到端耗时报告吞吐量、P95/P99，附服务端辅助指标。基线与优化使用相同机器、数据和负载；报告 CPU、内存、磁盘和软件版本，分别报告数据库、搜索进程、应用内存和相关持久卷占用。

## 第四轮已确认

- 种子生成使用固定随机种子和可配置时间基准；初始化命令只允许写入空实验数据库。重置必须显式指定 `--reset`，只作用于指定实验数据库。
- 压测数据单独生成，每轮压测前恢复相同初始状态。
- V1 仅支持种子账号登录，密码安全哈希，提供有有效期的访问令牌，Swagger UI 支持令牌认证；暂不提供公开注册、刷新令牌或退出后的令牌撤销。
- 扩展属性只允许字符串、数值、布尔值及这些类型的数组，不允许嵌套对象，并限制数量、名称和值长度。标准字段独立保存，不能被扩展属性覆盖。
- 每件商品包含 1–9 个 HTTP/HTTPS 图片地址，不验证图片实际可访问性。
- 同义词表和固定验收案例版本化，至少覆盖自行车／单车／脚踏车，验证标题、描述及同时命中。搜索总数和结果采用相同有效性条件，但不承诺请求级事务快照；每条结果在校验时有效在售。
- 自动下架验收预置已过期及即将到期条目，证明期限立即阻止在售查询与成交，并证明 TTL 最终删除条目而商品档案仍保留；记录数据库证据及实际清理延迟，不承诺固定清理时限。
- 不增加作业未要求的 P95/P99 门槛，报告实测值及错误率；8 项功能脚本使用统一测量方法，保留原始输出。
- 课程实验报告先采用 Markdown，持续记录选型、设计、实验及实测结果；本轮不制作 Word 文档，学校封面模板不作为当前工作依赖。


## V2 已交付核验（2026-10-11）

本机 A/B/C 各三轮均独立完成 30,000 件新增按时成交及逐商品/卖家一致性核验；50 位实际就绪用户、600 秒硬截止、相同完整恢复数据与资源口径已经验证。八功能各100样本、十个TTL样本、独立竞争/同键、资料缓存并发编辑及真实故障恢复、六组A/B详情及两组C热点、跨实例认证/幂等与分发均保留完整材料。

[Markdown实验正文](v2-report.md) 与 [统一证据索引](validation/v2-evidence.json) 链接实际结果、全部失败/分类修正与源版本复用限制。`scripts/validate-v2.py --mode verify --output NEW_DIRECTORY` 离线重算，`--mode reproduce` 逐阶段独占复现并限定清理自己创建的资源。部署A/B/C V1外部行为回归在独立原始200k种子fixture通过，不混入230k正式性能样本。

Redis实验没有证明必然改善，热分散缓存实际0命中且自然错误如实保留；C增加应用总资源和代理，结果不是相同总资源的效率结论。物理第二台机器仍未验证，最后评估为待考虑；不纳入本轮必交，也不宣称跨机器能力已经通过。
