Run A/disabled, B/cold and B/hot for each of hotspot and dispersed, using the same restored dataset and seed (default42). A hotspot100 reads the first100 entries of a deterministic shuffled sorted complete product ID pool. Dispersed uses all230,000 archives, including180,000 historical sold products. Every VU `i` reads `pool[(i + 50 * sequenceIndex) % poolSize]` serially. Configurations share exactly this potential sequence; elapsed-time experiments consume different prefix lengths when throughput differs. Every raw request records VU, sequence index, pool position and product ID; summaries preserve each consumed prefix. The pool and its hash are saved, so paired runs can be checked without assuming equal completion counts.

The runner requires an explicit isolated-cache confirmation and exact Docker project ownership, and verifies running/healthy application instances' actual DB/cache configuration. It resets that dedicated Redis DB for each run and confirms `DBSIZE=0`; readiness probes only `/health`, so cold preparation does not read products. Hot preparation reads every involved ID once with50 workers, saves raw HTTP outcomes and elapsed preparation time, and retains actual Redis memory/key count/evictions/configuration. This can exceed128MiB and does not imply all items remain cached. Full-pool warming time is separate from the60-second window.

After preparation, the same #17 recorder captures30seconds of idle by default and the real detail interval, using client wrapper and descendant PIDs. Window coverage includes start/deadline boundaries; two seconds after client exit are retained to cover the last boundary. Exact query count and returned BSON bytes come from successful detail response headers, including product projection, seller, eligibility and recent history queries. These bytes are returned BSON sizes, not disk reads or network traffic. Cache hits/misses/fallbacks and per-request errors, transport/business errors, median/P95/P99 (nearest rank), throughput and late receipts are computed from raw gzip JSONL. Per-request Redis error instrumentation is pending real red/green validation; disabled A assumes zero cache errors.

Outputs include initial/final business counts, gzip command evidence and fixed pool, prewarm receipts, Locust CSV/history/HTML/log, request receipts, preparation timing, window readiness, per-request telemetry summaries, Redis state, idle resources and load resources/storage/environment. `experiments/summarize_details.py` and #17 `--summarize --window` recompute aggregates. Detail reads are independently checked not to change product/sold/transaction counts. No cache speedup is a passing condition; normal runs reject fallback/errors and preserve them as evidence.
